# Publishing the website

The authored source is `src/` (HTML template, stylesheet, TypeScript scripts, i18n data, assets). `dist/` is the built site that GitHub Pages serves. It is generated by `npm run build`, ignored by Git and never edited by hand:

https://ivan-esteban23.github.io/the-reference-edit/

## Building

```sh
npm ci
npm run typecheck
npm run build
```

`scripts/build.mjs` inlines the stylesheet and every TypeScript script into a single self-contained `dist/index.html`; no bundled chunks are produced on purpose, because the Pages preparation and the worker precache list only understand the single-file layout (see `Pages path handling` below). Everything else in `dist/` is copied unchanged from `src/`, including `dist/sw.js`, which is a verbatim copy of `src/sw.js`. `npm run build` is the only way to change published output: change `src/` and rebuild.

The Pages setting remains **Deploy from a branch → `preview/phone` → `/ (root)`**. Despite its historical name, that branch is generated deployment output. Do not merge it into `main` or edit the generated files manually.

## Continuous integration

`.github/workflows/ci.yml` is the single test definition for the repository. It runs on pull requests and by manual dispatch, on the Node versions the project supports: the `>=22` floor from `package.json` and the current `24` release. Each job installs with `npm ci`, selects the runner's Google Chrome for the browser harness, runs the documented `npm test` command, and uploads `/tmp/reference-regression-results/` even when a suite fails. The workflow has read-only repository permissions, cannot publish, and cancels superseded pull-request runs.

`npm test` includes `tests/workflows.mjs`, which checks this contract. It verifies that the CI matrix covers the declared Node floor, every `tests/*.mjs` suite is still reachable through `npm test`, the workflow keeps full history for the historical fixtures and read-only permissions, and the deployment workflow delegates testing instead of maintaining a second suite list. Dependency updates are scheduled through `.github/dependabot.yml` with weekly checks for `npm` and `github-actions`, grouping minor and patch updates to minimize review noise.

## Automatic publication

`.github/workflows/pages.yml` runs on pushes to `main` and by manual dispatch. Its `test` job calls the reusable CI workflow, so both supported Node versions must pass before publishing. PRs run CI directly and never trigger this workflow. After a successful test run on `main`, the publishing job:

1. Prepares a fresh static snapshot outside the checkout with `scripts/prepare-pages.mjs`.
2. Updates the generated `preview/phone` branch using a normal commit/push, preserving its history.
3. Explicitly requests a GitHub Pages build. This is necessary because pushes made with the workflow's `GITHUB_TOKEN` do not trigger Pages builds automatically.


Publication uses the workflow token with `contents: write` and `pages: write`, without a personal access token or repository secret. CI tests have read-only repository access and cannot publish. A failed test on either Node version blocks the publishing job. Publishing requests are serialized for `main`.

On first merge of the workflow, inspect **Actions → Test and publish website**, then the Pages build. The publishing job must succeed and the Pages build must complete before claiming that a merge is live. A successful local test alone does not validate GitHub's deployment permissions. If repository policy denies the workflow token's requested permissions, adjust the Actions policy in GitHub rather than adding credentials to source.

The workflow can also be run manually from `main` using **Actions → Test and publish website → Run workflow**. If the explicit Pages-build request fails after the deployment-branch push, rerun the failed job; it is safe to prepare a new snapshot and commit. The existing live site stays available until Pages publishes a successful build.

## Pages path handling

The application source uses root URLs. Pages hosts this project below `/the-reference-edit/`, so the preparation script adjusts the manifest, worker scope, shell paths and root links in the generated output. Curated source records and all binary assets remain unchanged. It scopes worker caches to this Pages application and cleans up the previous phone-preview cache, preserving unrelated origin caches. User storage stays on the same origin and is not reset by publication.

To prepare a local snapshot without modifying the source checkout:

```sh
pages_directory=$(mktemp -d)
node scripts/prepare-pages.mjs "$pages_directory/site" /the-reference-edit/ "$(git rev-parse HEAD)"
```

The output directory must be fresh and outside the checkout. The script does no transpilation, dependency installation or font/image conversion, and it refuses to prepare a snapshot when `dist/` has not been built. Serving `dist/` directly is normal local development.

`node tests/pages.mjs` verifies scoped routing, manifest/worker registration, installability, cache cleanup, fonts/images, local favorites/personal records and offline navigation against the prepared snapshot.

## Site hosting previews

`.openai/hosting.json` publishes the local `dist/` directory. That tool uploads files as they are on disk: it does not run `npm run build`. Run `npm run build` before preparing or refreshing a preview, otherwise the upload is the previous build or nothing at all. `npm test` builds first, so a green local test run leaves a current `dist/` ready to upload.


## Editorial gallery catalog and offline paths

`src/data/references.json` reaches `dist/` and the prepared snapshot byte-for-byte. The preparation script scopes the HTML's catalog URL and worker shell URLs; it does not rewrite image paths inside this JSON. The gallery explicitly resolves each validated canonical `/images/references/...` value relative to the application root derived from its catalog URL, so the same catalog works at `/` and `/the-reference-edit/`.

The catalog and all three local editorial JPEGs are required precache assets. Bump the source worker cache version whenever the UI, catalog or an illustration changes. Failed downloads/writes leave an existing worker installation active; offline gallery availability requires a completed installation and retained browser cache. Pages and worker migration tests exercise the project path, offline images and upgrades. The gallery test runs in the existing read-only CI test job; publication conditions and permissions remain unchanged.
